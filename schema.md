# Wiki Schema

This file defines the page types, naming, frontmatter, and the paper-source contract for `wiki/`. The checks in `tools/wiki/` enforce the structural parts; see `tools/wiki/README.md` for the exact rules each script applies.

## Page Types

| Type | Directory | Purpose |
|------|-----------|---------|
| source | wiki/sources/ | One page per paper, written from its full-text parse |
| concept | wiki/concepts/ | Techniques, system-model components, metrics, phenomena, frameworks |
| entity | wiki/entities/ | Recurring authors and named tools |
| finding | wiki/findings/ | Individual empirical results or observations from one source |
| synthesis | wiki/synthesis/ | Cross-cutting summaries and conclusions over a track or design space |
| comparison | wiki/comparisons/ | Side-by-side analysis of comparable methods, formulations, or setups |
| methodology | wiki/methodology/ | Research methods and solution protocols shared by several sources |
| query | wiki/queries/ | Open questions under active investigation |
| thesis | wiki/thesis/ | Working hypotheses and their evolution over time |
| overview | wiki/ | High-level project summary (`wiki/overview.md`, one per project) |

Other files under `wiki/` are not typed pages:

- `wiki/index.md` and `wiki/log.md` are navigation and history pages (formats below).
- `wiki/references/` holds the reference database and recommendations generated by the `mec-reference-scout` tools (`type: reference-database` and `type: recommendations`). Do not edit them by hand.
- `wiki/.grounding/` holds the grounding evidence sidecars described under [Grounding Evidence](#grounding-evidence).

## Naming Conventions

- Files: `kebab-case.md`. Page basenames must be unique across `wiki/`, because wikilinks resolve by basename.
- Sources: `author-year-slug.md`, using the first author's surname (e.g., `zeng-2019-rotary-wing-energy-min.md`). When the parse gives no year, omit it (e.g., `wang-gai-isac-physical-layer.md`); never invent one.
- Concepts: descriptive noun phrases (e.g., `soft-actor-critic.md`, `rotary-wing-propulsion-energy-model.md`).
- Entities: authors as `given-family` (e.g., `geng-sun.md`); tools by official name (e.g., `pytorch.md`).
- Findings: descriptive slug (e.g., `acbft-throughput-increase.md`).
- Synthesis: track or design-space name (e.g., `maritime-mec-architectures.md`).
- Comparisons: compared items or dimension (e.g., `j-ppo-vs-pdqn.md`, `game-theoretic-offloading-formulations.md`).
- Methodologies: method name (e.g., `lyapunov-guided-drl.md`).
- Queries: question as slug (e.g., `query-when-does-dro-beat-drl-for-csi-uncertainty.md`).
- Theses: hypothesis as slug (e.g., `decomposition-beats-end-to-end-drl-in-mec.md`).

Reuse existing slugs and tags. Do not create a near-synonym of an existing concept, and do not merge two authors by name alone.

## Frontmatter

All typed pages must include YAML frontmatter and an `# H1` title in the body:

```yaml
---
type: source | concept | entity | finding | synthesis | comparison | methodology | query | thesis | overview
title: Human-readable title
tags: []
related: []
created: YYYY-MM-DD
updated: YYYY-MM-DD
---
```

`type` must match the page's directory. `related:` must not list the page itself. Bump `updated:` on every content edit.

Source pages also include the `source` tag and:

```yaml
authors: []
year: YYYY
url: ""
venue: ""
```

When the parse omits a field, write `not in parse` or leave it empty; never guess.

Paper-backed source pages also include exactly one of:

```yaml
modeling_card: required
```

```yaml
modeling_card: not_applicable
```

Entity pages carry the `author` or `tool` tag. Synthesis pages carry the `synthesis` tag.

Thesis pages also include:

```yaml
confidence: low | medium | high
status: speculative | supported | refuted | settled
```

Finding pages also include:

```yaml
source: "[[source-slug]]"
confidence: low | medium | high
replicated: true | false | null
```

## Paper Source Contract

### Evidence authority

- A paper source is grounded in the Markdown parse under `raw/sources/<folder>/`: a title-named `.md` (most folders), a citekey-named `.md` from newer ingests (e.g., `kool2019iclr.md`), or a legacy `full.md`. The companion PDF resolves parse omissions or corruption.
- The workflow remains raw-parse driven. It does not read `.bib` companions, does not name source pages by citekey, and does not add `source_id`, `source_type`, `base_confidence`, or `lifecycle` fields.
- Every Modeling Quick-Use Card symbol, expression, and numerical statement, and every sentence in the Related Work paragraph, must be traceable to the raw parse or companion PDF.

The current `wiki/sources/` corpus is paper-backed and follows this contract. If a future source is a talk, book, blog post, or other non-paper medium, revise the schema with an explicit discriminator before adding it rather than silently forcing the paper contract onto that page.

### Modeling-card applicability

Use `modeling_card: required` when the paper's central contribution contains an application-specific, reusable decision or control model with all of the following:

- explicit decision variables or actions;
- an objective, utility, cost, or reward;
- constraints, a feasible domain, or state/action limits.

Qualifying formulations include MINLP, convex, stochastic, or robust optimization, games, MDP/POMDP models, scheduling, and trajectory control when those elements are present.

Use `modeling_card: not_applicable` for surveys and tutorials, foundational algorithm papers, pure prediction, channel-estimation, measurement, or detection papers, and systems or protocols without a reusable decision model. A training loss or evaluation metric alone does not qualify. These exclusions take precedence over generic mathematical or RL background in a foundational-method paper.

For a borderline paper, inspect the raw parse or PDF before deciding. A title, tag, or `System model` heading is not evidence of applicability.

### Canonical section order

Paper source pages follow this order:

```text
Citation
TL;DR
[Modeling Quick-Use Card, only when modeling_card: required]
Related Work Paragraph
Problem framing
System model
Method
Key findings
Limitations / future work
Relation to the corpus
Raw artifacts
```

`TL;DR` is the positioning section. Do not add a separate one-line-positioning heading. Existing semantically equivalent detailed headings (e.g., `Problem` for `Problem framing`) may remain; valid prose does not need to be rewritten solely to rename a heading. The exact relative order of `Citation`, `TL;DR`, the optional card, and `Related Work Paragraph` is mandatory. A `not_applicable` page must not contain a Modeling Quick-Use Card.

`Raw artifacts` lists the parse path as an inline code span, e.g. `` `raw/sources/<Folder>/<Folder>.md` ``, followed by a note that the PDF and figures are in the same folder. The curation and manifest tools resolve each page to its parse through this block.

### Modeling Quick-Use Card

Copy this English template only when `modeling_card: required`:

```markdown
## Modeling Quick-Use Card

> Reuse in a system model or problem formulation section: scenario, model, decisions, constraints, and algorithm.

**Scenario**: <network topology, nodes, application, assumptions, multiple-access scheme, and channel model>.

**Problem & objective**: <problem name or number, problem type, objective formula, and optimization metric>.

**Decision variables**:

| Variable | Symbol | Type / range | Meaning |
|---|---|---|---|
| <variable name> | $<symbol>$ | <binary, continuous, or integer range> | <meaning> |

**Constraints**:

| ID | Meaning and key expression |
|---|---|
| C1 | <constraint meaning and expression> |

**Algorithm**: <method family and step-by-step solution chain>.
```

Do not leave core fields or table cells blank, and do not use `N/A`, `TBD`, `...`, or a dash as a substitute for grounded content. The card is a concise reusable view, not a replacement for the detailed model and method sections. Its symbols and formulas must match those sections and the paper.

Additional rules:

- Use the paper's own notation and constraint labels (e.g., `(31b)-(31i)`), not invented `C1`-`Cn` labels, when the paper numbers its constraints.
- List only true decision variables. Given inputs, model dynamics, and post-solution rules are not decisions or constraints; label such rows `Model rule`, `Algorithm rule`, or `Simulation setting`.
- Tables are split on `|`, so write absolute values and set sizes in math as `\lvert x \rvert`.
- The constraints label is exactly `**Constraints**:`; put notes in a `| Note | ... |` row.
- The `Problem & objective` line must contain a math expression taken from the paper. When a `required` paper has no formal optimization problem, quote its own metric or model equations and state that no formal problem exists, rather than inventing one.

### Related Work Paragraph

Every paper-backed source page contains this section immediately after `TL;DR` and the optional card:

```markdown
## Related Work Paragraph

> Ready to reuse in a literature review. Replace `[x]` with the formal citation number.

Author et al. [x] studied <the paper's stated problem or scheme> in <the paper's scenario>. They formulated <the problem and objective> and proposed <the method and its key steps>. Simulation or experimental results show <the paper's reported findings>.
```

The prose must:

- be one English paragraph of 4-8 sentences;
- cover scenario, problem and objective, method steps, and the paper's principal reported results;
- preserve Abstract and Introduction terminology where possible;
- use `[x]` at the author citation;
- contain no internal wikilinks, CJK text, em dash, or `--`;
- state only what the paper did and reported, without wiki-authored comparison, evaluation, or gap claims.

Paper-reported comparisons are allowed when worded as reported results. Name the paper's actual baselines, and report a baseline that wins on some metric when the paper says so. The structural audit cannot establish factual grounding, so sentence-level evidence review remains mandatory.

## Grounding Evidence

Grounding review records its evidence in JSON sidecars under `wiki/.grounding/`, one file per review batch, named `source-schema-evidence-<batch>-<topic>.json`:

```json
{
  "entries": [
    {
      "slug": "zeng-2019-rotary-wing-energy-min",
      "modeling_card": "required",
      "review_status": "grounded",
      "classification_evidence": [
        {"path": "raw/sources/<Folder>/<Folder>.md", "lines": "120-148", "note": "Problem (P1) and constraints"}
      ],
      "related_work_evidence": [
        {"path": "raw/sources/<Folder>/<Folder>.md", "lines": "5,410-422", "note": "abstract and results"}
      ]
    }
  ]
}
```

- `modeling_card` must equal the page's frontmatter value.
- `path` is the page's resolved parse path in POSIX form; `lines` are 1-based, in-bounds, comma-separated lines or ranges; `note` is non-empty.
- Both evidence lists are non-empty, and a slug appears in only one sidecar.
- A newly curated source page needs its own sidecar entry so that `source_schema_manifest.py --require-grounded` keeps full coverage.

## Index Format

`wiki/index.md` lists all pages grouped by type, with topic subsections where a type is large. Each page has exactly one primary entry:

```text
- [[page-slug]] — one-line description
```

## Log Format

`wiki/log.md` records activity in reverse chronological order, newest first. It is the only page that may describe batches, passes, or runs:

```text
## [YYYY-MM-DD] Short description of the change

- Action taken, pages affected, evidence, and gate results
```

## Cross-referencing Rules

- Use `[[page-slug]]` syntax to link between wiki pages. Never leave a dangling link or link a page to itself.
- Every page appears in `wiki/index.md`.
- Queries link to the sources and concepts they draw on.
- Synthesis pages cite all contributing sources via `related:`.
- Findings link back to their source via the `source:` frontmatter field.
- Thesis pages reference supporting and refuting findings via `related:`.
- Methodology pages are cited by the findings that used them.

## Evergreen Wording

Every page except `wiki/log.md` describes the corpus as it is, not how it was built. Do not mention batches, passes, run dates, ingest order ("paper #N"), or plans for future curation. A paper's own future-work section is domain content and is allowed. `tools/wiki/process_refs.py` enforces this rule.

## Contradiction Handling

When sources contradict each other:

1. Note the contradiction in the relevant concept or entity page.
2. Create or update a query page to track the open question.
3. Link both sources from the query page.
4. Resolve in a synthesis page once sufficient evidence exists.

## Research-Specific Conventions

- Keep the thesis pages updated as evidence accumulates; they are living documents.
- Every finding should assess replication status when known.
- Methodology pages explain the *why* (rationale), not just the *how*.
- Distinguish between direct evidence and inference in finding pages.
- Separate theorem from approximation, global from local results, and simulation from measurement when reporting a paper's claims.
